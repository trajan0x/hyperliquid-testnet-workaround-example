Bridging USDC to fresh addresses on HyperCore testnet

Why deposits vanish, a crude workaround that does work, what did not, and what works for EOAs. Code: github.com/trajan0x/hyperliquid-testnet-workaround-example

On HyperEVM testnet, CoreDepositWallet.depositFor to a fresh address looks fine on the EVM side. The transaction succeeds and the USDC is burned. On HyperCore nothing arrives. This came up in a Discord question and in hyperliquid-dex/node#138 (comment).

1. Why testnet bridge deposits fail

Circle documents two testnet rules (source). The recipient must already exist on HyperCore mainnet. An address that passes can still receive at most 1,000 testnet USDC. If either check fails, the deposit is dropped without an error.

2. The workaround: skip the bridge, verify on Core

Each user gets a deposit contract at a CREATE2 address with the user as salt. The address is known before anything is deployed, and HyperCore will hold funds for it right away. On testnet we fund it with a Core-side spotSend from a faucet wallet, so the bridge and its checks are never involved.

The contract does not believe EVM events. It reads its own spot balance from the spotBalance precompile at 0x...0801. CoreWriter actions are processed after the EVM block that emits them, so the contract checks the result of an action in a later block. Crediting the user works the same way. The sweep sends the funds out in one block. A later block confirms they left, and only then is the user credited. The user cannot act in between.

3. One-time activation

The contract starts disabled. To activate it, a small amount (1 USDC here) is sent in through the exchange API. The contract sends it back out through CoreWriter and records its balance at that moment. In a later block, confirmActivation() checks that the balance dropped by that amount. Only then does the contract accept real actions. This proves the contract's CoreWriter path works before anything valuable depends on it.

4. Making the address a "mainnet user" did not help

If the only problem is "recipient must exist on mainnet", give it mainnet state. The factory is deployed through the deterministic CREATE2 deployer 0x4e59...956C, which exists on both chains. Its constructor takes only the owner, and per-chain settings go into storage later. So the factory, and every deposit address it makes, has the same address on mainnet and testnet. On mainnet we sent the address 2 USDC, deployed the replica, and its initializer added an operator API wallet through CoreWriter. That API wallet can sign gasless L1 actions for the address.

All of that worked. Testnet deposits to the address still did not arrive. We then tried real mainnet bridge history. We bridged 5 USDC with mainnet depositFor to the deposit address and to a brand-new EOA, and both landed on mainnet Core. Testnet deposits to them failed 5 minutes, 40 minutes, and about 24 hours later, including after the EOA got a testnet Core account. Our old wallet was credited in seconds every time. Whatever testnet checks, we could not create it: a Core account or bridge deposit made the same day does not pass. Nothing from the failed deposits ever showed up later.

5. What does work for EOAs: native HYPE

The limit is specific to USDC through CoreDepositWallet. We sent 0.01 HYPE from a brand-new testnet EOA (no mainnet history, never on Core) to the HYPE system address 0x2222...2222. The testnet ledger recorded it at once. The info API still showed the address as missing with no balance, because the address had no Core account. When another wallet sent the EOA a little USDC on Core, the account was created and the 0.01 HYPE was already there. From then on HYPE moved both ways within seconds.

So for testnet EOAs that hold assets on HyperEVM and have never touched Core: have any wallet with testnet Core USDC send each one a small amount on Core (the sender pays a 1 USDC new-account fee). After that, HYPE moves freely between HyperEVM and Core. USDC through testnet depositFor still does not work for them, so move USDC with Core-side sends.

Caveats

This is crude testnet code and has not been audited. The first transfer to any new Core address costs the sender 1 USDC, so the sweep target must already exist on Core or the sweep is rejected and the deposit address stays locked. Accounts in unified-account mode reject spotSend; the scripts fall back to sendAsset. API wallets cannot move funds out of an account, because transfers are user-signed and move the signer's own funds.
